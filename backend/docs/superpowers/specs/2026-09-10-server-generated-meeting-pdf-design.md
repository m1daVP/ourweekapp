# Server-generated meeting PDF export

## Goal

Replace the client-side print view, which renders raw Markdown inside a `pre` element, with a branded PDF generated by the API. Every client receives the same layout and uses its normal platform download or share capability to deliver the generated file.

## Scope

- Add a Premium, authenticated meeting-PDF export endpoint.
- Render a calm, readable OurWeek document from structured meeting data.
- Preserve current workspace authorization and private-note exclusion.
- Require the meeting to have synced to the API; offline and unsynced meetings cannot be exported as PDF.
- Replace the web print-window flow with authenticated binary retrieval and platform-appropriate delivery on web, Android, and iOS.
- Leave the existing local text and Markdown exports unchanged.

## Non-goals

- Rendering or parsing user-authored Markdown into the PDF.
- Generating PDFs on the client or in a native WebView.
- Exporting private notes, provider metadata, internal IDs, or other private fields.
- Supporting unsynced or offline PDF export.
- Introducing a database migration.

## API contract

The API exposes `POST /v1/exports/meeting/pdf` with the existing `meetingId` request body. It uses the same authentication, minimum `adult_member` role requirement, and `export` feature entitlement as the current meeting-export route.

On success, it returns a binary body with:

- `Content-Type: application/pdf`
- `Content-Disposition: attachment; filename="ourweek-<date>-<slug>.pdf"`
- a safe filename derived from the meeting title and completion/update date

Errors retain the current stable JSON error format:

- `401` for no valid session;
- `403` for a viewer or no Premium export entitlement;
- `404` when the meeting is not in the requesting workspace, including when the client is asking for an unsynced local-only meeting;
- `422` for malformed requests;
- `500` for an unexpected rendering failure, with the implementation logging only non-sensitive context.

The endpoint returns bytes directly rather than base64 or a temporary public URL. This avoids persistence and public access to sensitive family content.

## Rendering design

The export module owns the transformation from already-authorized `MeetingDto` data into a PDF document model and from that model into bytes. The document is composed from structured fields, never from the existing Markdown export.

The first page begins with an OurWeek masthead, meeting title, date, and status. When an AI summary exists, it appears as an at-a-glance summary with clearly separated topic, tension, agreement, task, and next-week-focus lists. The remaining document presents meeting sections in order, with the section title and prompt followed by distinct notes, task, and agreement blocks. Tasks include their title, optional description, responsible participants, due date, and status; agreements include their text, optional description, and participants.

The design uses restrained OurWeek branding, typographic hierarchy, light section dividers, repeatable page headers/footers, and safe page-break rules so that individual task and agreement entries are not split awkwardly. Empty content is omitted instead of printed as placeholder prose. A small footer states that private notes are excluded.

The server will use a maintained Node PDF library that draws the document directly. This keeps rendering deterministic and avoids packaging or operating a headless browser/Chromium runtime in the Fastify deployment. The chosen library must support embedded fonts, pagination, and streaming/buffer output.

## Privacy and authorization

The existing `ExportsRepository.findMeetingForExport(workspaceId, meetingId)` continues to be the only repository lookup. The service must call it only after role validation. Its workspace-scoped query prevents cross-household lookup.

Before any document model is built, the existing export sanitizers remove private-marked notes and fields. The renderer receives only this sanitized content. Participant labels must use the meeting's synced display data and must not expose participant IDs in the resulting PDF.

No PDF files, source content, tokens, or authorization headers are written to server logs. The server returns the rendered bytes without storing them.

## Client delivery

Add a dedicated API helper that performs an authenticated request and returns a `Blob` plus the filename from `Content-Disposition`. The generic JSON API helper remains JSON-only; binary parsing and safe error decoding are isolated in the new export helper.

The export service changes PDF export from synchronous browser-print behavior to an asynchronous request. It constructs a `MeetingExportFile` using the API's PDF bytes and filename, then routes it through the existing file delivery abstraction.

Web downloads the PDF or uses the Web Share API when available. Android and iOS write the PDF bytes to a cache file and invoke the native share sheet; both platforms delete the temporary file afterward. The UI shows progress while the PDF is being generated, disables duplicate activation, and reports a clear retryable error for network, sync, or rendering failures. Existing text and Markdown copy/save actions remain local and offline-capable.

## Testing and verification

Backend tests cover the binary endpoint's authentication, role and Premium feature checks, invalid payload handling, workspace scoping, private-note exclusion, content type, content disposition filename, and a valid PDF header in the returned bytes. PDF-renderer unit tests use a representative meeting with AI summary, notes, tasks, agreements, long values, and empty sections to validate document-model shaping and privacy filtering.

Frontend tests cover authenticated binary retrieval, JSON error decoding, filename handling, loading and error state in the export action, and delivery through browser/native branches. Manual QA covers browser download/share, Android native sharing, and iOS native sharing, plus multi-page PDFs, accented and Ukrainian text, long task lists, no-summary meetings, and an offline or unsynced meeting error.

Run backend `npm run typecheck`, focused export tests, and `npm test`. Run frontend `npm run typecheck`, focused export tests, `npm run build`, and `npm run check`. Native builds additionally need real-device share-sheet QA after the Capacitor sync.
